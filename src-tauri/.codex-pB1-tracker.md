## Pattern findings
- Canonical request commands validate every read fail-closed, dedupe unsettled requests, and persist the intent last.
- Canonical dispatchers CAS `Pending -> Starting`, revalidate after claim, execute through the existing host seam, then persist a terminal result; startup sweeps stale claims to `FailedStale` and never retries them.
- A dedicated request-status read is required: `get_remote_execution_status` reports scheduler state but cannot distinguish pending, dispatcher rejection, or failed host execution for one intent.

## Design decisions
- Use separate execution-resume, task-resume, task-restart, and group-resume intent variants behind domain-appropriate dispatch execution because their local seams are materially different (scheduler restoration vs AppHandle task entry actions vs restart recovery classification vs bulk traversal).
- Expose dedicated poll reads so remote API wrappers can settle to the same response type as the local command without claiming success at enqueue time.
- Preserve each local API invoke branch byte-for-byte; remote branches are additive literal command names.
- Four intent commands are approved because execution resume, task resume, task restart, and group resume have materially different validation/result shapes; task-scoped rows should share one repository/dispatcher with an action enum if the dispatcher precedent supports it.
- Dedicated poll-status reads are required for each intent family because scheduler/task state cannot distinguish pending, dispatcher refusal, host failure, or stale-claim settlement.
