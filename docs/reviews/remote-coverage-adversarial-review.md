# Remote Client ↔ Host Coverage — Adversarial Review

**Branch:** `feat/remote-multi-env` · **Date:** 2026-08-01 · **Scope:** what a paired remote client can actually do against a host across **conversations, automations, ticketing, and GitHub management** · **Method:** 23-agent adversarial workflow (see [Method](#method))

## Executive summary

The transport and read plane of the remote feature is in genuinely good shape: transcripts, pagination, the sidebar inbox twin, the three spawn-free intent flows (start / continue-idle / stop) with host-owned dispatchers and poll-to-terminal semantics, pending-gate hydration, and the Durable/Transient event split all survived adversarial reading. The problems are concentrated in the **write plane and in surfaces that were never taught about remote environments** — and they cluster into five systemic patterns rather than dozens of unrelated bugs:

1. **The "viewer with brakes" contract is broken at both brakes.** The client still invokes the raw command names (`resolve_permission_request`, `resolve_user_question`) that the facade deliberately does not register, while the argument-pinned twins built for exactly this (`approve_permission_request` / `deny_permission_request` / `answer_user_question`) have **zero production call sites**. A paired device can neither approve *nor deny* a permission gate, cannot answer an agent question — and the question failure is mislabeled "Agent session expired" while the banner is cleared over a still-blocked agent. The gates render *enabled* because they point at the ops the surfaces never call.
2. **Liveness is systemically blind.** Every run-status read the chat/sidebar consumes (`get_agent_run_status_unified`, `get_agent_conversation_runtime_statuses`, `is_agent_running`) is a detector-c refusal, polled forever with errors swallowed; the one *registered* liveness read (`get_agent_conversation_runtime_index`) is consumed by a single card. A remote client therefore believes every conversation is idle — which also hides the Stop button, the third brake.
3. **Whole surfaces shipped with no remote gating.** The Automations page (12 mutating call sites, 4 permanently unavailable, "Run now" gated by the *wrong* op and rendering enabled), the Agents task-detail views (an ungated fork of the gated originals — and the fork is what the remote-primary Agents pane renders), plan approval / ideation acceptance (mandatory product gates that die on unmounted POST routes with a bare "Not Found"), and most GitHub surfaces (false "install gh" advice about the *client's* auth, a permanent Git-access false alarm, optimistic merge-retry).
4. **A misattribution family: host state rendered through client-local lenses.** Ticketing shows the host's configured providers as "Not configured", linked tickets silently vanish, GitHub reports the authenticated host as unauthenticated — all because settings/status reads fail or answer about the wrong machine and the UI treats absence as truth.
5. **An unaudited side door: Tauri plugin commands route to the host.** The `@tauri-apps/api/core` alias is global, so all seven plugins (`opener`, `dialog`, `fs`, notifications, …) invoke through the remote wrapper — invisible to the P-11 census. Concretely today: "Open in browser" on a ticket opens the browser **on the host Mac**, and enabling desktop notifications remotely is a silent no-op.

Cross-cutting: unknown-outcome reconciliation (`REMOTE_TIMEOUT_UNKNOWN`) exists for only ~2 of ~90 mutating ops, and read-only mode reaches the UI through a single hook that covers a fraction of mutation surfaces. Two headline claims were **killed** in verification (the "liveness fails open" and "timeout reads as hard failure" claims — details per domain), which is the point of the adversarial pass: what remains below survived a skeptic instructed to refute it.

## Conversations

The read half of this domain is genuinely well covered: the spawn-free transcript/list/sidebar twins, the three intent surfaces (start / continue-idle / stop) with host-owned dispatchers and terminal-state polling, and the Durable/Transient event classification all hold up under adversarial reading, and the folder-add and attachment-preview gaps are honest and documented. The write half breaks down at the two gates that matter most: the client still calls the RAW `resolve_permission_request` and `resolve_user_question` names, neither of which is a facade op — so on a paired device a permission gate can be neither approved NOR denied (the "viewer with brakes" boundary the ledger designed the pinned `deny_permission_request` op for is unreachable), and answering an agent question fails while the UI reports "Agent session expired" and deletes the banner out from under a still-blocked agent. Meanwhile `permissionApprove`/`questionAnswer` are gated against ops the surface never calls, so both render `enabled`. Second cluster: every run-liveness read (`get_agent_run_status_unified`, `get_agent_conversation_runtime_statuses`, `is_agent_running`) is a documented detector-c refusal, and no client code falls back to the registered `get_agent_conversation_runtime_index` — so after a cold hydrate a remote client believes every conversation is idle, which also hides the STOP brake that was deliberately registered at `ui:operate`, and one of those reads fails OPEN to "not running". Third: queued-message delete/edit optimistically mutate local state and swallow the host failure, so a "deleted" turn is still delivered and an "edited" one is delivered twice. A tail of ungated affordances (mode switch, fork, archive, mute, attachment upload, persona switch) reach unregistered commands and degrade to error toasts instead of the honest disabled state the gate machinery exists to produce.

### Findings

#### [CRITICAL] A paired client can neither approve NOR deny a permission gate — it sends the one command name the facade deliberately does not register

***CONFIRMED** (high confidence)* · `frontend/src/api/permission.ts:46`

**Claim.** `permissionApi.resolveRequest` invokes the raw `resolve_permission_request`, which is absent from `facade_ops`; the host only exposes the argument-pinned twins `approve_permission_request` / `deny_permission_request`, and no production call site in the frontend ever sends either name.

**User-visible failure.** On a paired client an agent hits a permission gate. The dialog appears (the `permission:request` Transient frame and `list_pending_permission_gates` both work). The user taps Deny — the affordance the 'viewer with brakes' boundary explicitly promises every default-paired device — and gets the inline banner 'Unavailable on this host'. Approve behaves identically even with `ui:agent` granted. The gate cannot be resolved from the client at all; the host's agent stays blocked until someone walks to the host Mac.

**Evidence.** frontend/src/api/permission.ts:46 `await invoke("resolve_permission_request", { args: { request_id, decision, message } })`. `registry.rs:1057` registers `"deny_permission_request" => permission_commands::resolve_permission_request` and `registry.rs:1983` registers `"approve_permission_request"` against the same fn — the raw name is registered nowhere, and `find_spec` (registry.rs:557) matches `spec.name` exactly with no alias table (`invoke.rs:94`). docs/generated/remote-coverage-census.md:94 records the intent: "`resolve_permission_request` is `seam-resolved-via-remote-twin` … the facade already registers that exact fn twice". grep for `approve_permission_request|deny_permission_request` across frontend/src returns only `lib/remote/agent-gate.ts:115,170` (gate metadata) and its tests — zero invoke sites. The gate therefore resolves against an op that EXISTS: `agent-gate.ts:115 permissionApprove: "approve_permission_request"` → `enabled` with `ui:agent`, and `permissionDeny` sits in `INERT_AFFORDANCES` (agent-gate.ts:166) so Deny is never disabled at all. PermissionDialog.tsx:339 calls `resolveRequest` for both decisions.

**Verifier adjustment.** `permissionApi.resolveRequest` (frontend/src/api/permission.ts:46) invokes the raw `resolve_permission_request`, which the remote facade deliberately never registers (proved by `capability_ledger_tests.rs:868-872`); the host exposes only the argument-pinned twins `approve_permission_request` (registry.rs:1983) / `deny_permission_request` (registry.rs:1059), and no production frontend call site ever sends either name. Because `vite.config.ts` aliases `@tauri-apps/api/core` to the remote invoke wrapper and neither `local-only-commands.ts` nor `network-invoke.ts` rewrites the name, both Allow and Deny in `PermissionDialog.handleDecision` (PermissionDialog.tsx:328-345) reach the host as an unregistered command and fail with `REMOTE_COMMAND_UNAVAILABLE`. The gate is reachable remotely (permission:request is Transient per ralphx-remote-protocol/src/lib.rs:573, and `list_pending_permission_gates` is registered at registry.rs:719), so a paired client renders a live dialog whose every button is dead. Secondary: `get_pending_permissions` is also unregistered, so the mount-hydration and notification-center reopen reads fail silently on a remote client.

#### [CRITICAL] Answering an agent question is impossible remotely, and the failure is reported as 'Agent session expired' while the banner is deleted under a still-blocked agent

***CONFIRMED** (high confidence)* · `frontend/src/hooks/useAskUserQuestion.ts:279`

**Claim.** Every question raised through the MCP `ask_user_question` tool carries a `requestId`, so `submitAnswer` always routes to `resolve_user_question` — classified `Elevated`/`SpawnsProcess`, i.e. unreachable at every scope — while the `questionAnswer` gate points at the registered-but-never-called `answer_user_question`, so the chips render enabled.

**User-visible failure.** A remote user with `ui:agent` sees an agent question, picks an option and taps Send. The invoke fails with REMOTE_COMMAND_UNAVAILABLE, the app claims the session expired, the question disappears from the client, and the id is marked answered so the mount/reconnect hydration will not bring it back for 5 minutes — while the host's agent is still waiting on an answer nobody can now see it needs.

**Evidence.** frontend/src/hooks/useAskUserQuestion.ts:279 `api.askUserQuestion.resolveQuestion(...)` is taken whenever `response.requestId` is set, and useQuestionInput.ts:106 always sets `requestId: activeQuestion.requestId`; the legacy `answerQuestion` branch (line 288) is therefore dead for this surface. frontend/src/api/ask-user-question.ts:67 invokes `resolve_user_question`, absent from `facade_ops`. src-tauri/src/remote_server/capability_ledger.rs:1475 pins it `RiskClass::Elevated` / `PROCESS` with the comment 'unreachable at every scope'. frontend/src/lib/remote/agent-gate.ts:116 maps `questionAnswer: "answer_user_question"` — an op that IS in `facade_ops`, so `resolveAffordanceGate` returns `enabled` under `ui:agent`. The catch at useAskUserQuestion.ts:313-318 then runs `toast.error("Agent session expired — question is no longer active")` and `clearActiveQuestion(currentSessionId)`. `dismissQuestion` (line 346) swallows the same failure and records the id in `answeredRequestIds`, suppressing re-hydration for 5 minutes.

**Verifier adjustment.** severity → major — On a remote client granted `ui:agent`, the question-answer affordance renders enabled but every submit is unreachable: the gate points at the registered twin `answer_user_question` while the actual call is the unregistered `resolve_user_question`, so the invoke fails with REMOTE_COMMAND_UNAVAILABLE, is misreported as "Agent session expired", and the banner is cleared while the host agent is still blocked. Correction to the reviewer's evidence: the Send path does NOT poison `answeredRequestIds` on failure (that write is inside the try, after a successful await), so a later reconnect reconcile via `list_pending_question_gates` does restore the banner. The 5-minute hydration suppression applies only to `dismissQuestion`, which records the id before the failing call and swallows the error — that is the genuinely silent sub-case. Note also that within a session the banner does not come back on remount, because the mount/visibility hydration uses `get_pending_questions`, which is likewise unregistered remotely and its rejection is swallowed.

#### [MAJOR] Every run-liveness read is unregistered and nothing falls back to the registered runtime index, so a remote client believes an active conversation is idle — and the STOP brake is not rendered

***CONFIRMED** (high confidence)* · `frontend/src/components/Chat/IntegratedChatPanel.tsx:871`

**Claim.** `get_agent_run_status_unified`, `get_agent_conversation_runtime_statuses` and `is_agent_running` are all documented detector-c refusals, so after a cold hydrate or reconnect a paired client has no way to learn that a run is live; `agentStatus` stays `idle`, and the stop control is only rendered when it is `generating`.

**User-visible failure.** A user starts a long agent turn on the host, then opens the client (or the client reconnects after backoff). The cold hydrate uses `subscribe{afterSeq: H}`, so no pre-connect `agent:run_started` replays, and all three liveness reads 404. The conversation renders idle: no typing indicator, no activity label, and — because `shouldShowStop` requires `generating` — no Stop button, even though `request_remote_agent_stop` was deliberately registered at `ui:operate` so a default-paired device keeps its brakes. The user cannot stop the run until the agent happens to emit its next lifecycle event.

**Evidence.** IntegratedChatPanel.tsx:871 `chatApi.getAgentRunStatus` → api/chat.ts:1844 `get_agent_run_status_unified` (refusal at capability_ledger.rs:3413). useAgentConversationRuntimeStatus.ts:131 and useAgentSidebarRunningStates.ts:50 → `get_agent_conversation_runtime_statuses` (refusal at capability_ledger.rs:1897). useChatRecovery.ts:311/391/434 → `is_agent_running` (refusal at capability_ledger.rs:1888). `agentStatus` is read from the chatStore (IntegratedChatPanel.tsx:607) and is only written by lifecycle events (useAgentEvents.ts:455,678) or by those unregistered reads. AgentComposerSurface.tsx:469 `const shouldShowStop = Boolean(onStop) && isAgentGenerating && value.trim().length === 0`. The registered read that carries the same truth — `get_agent_conversation_runtime_index` with `lifecycle: 'running' | 'waiting' | 'queued'` — is consumed only by AgentsComposerWorkspaceChangesCard.tsx:826.

**Verifier adjustment.** On a COLD hydrate (every fresh client process, cursor invalidation, epoch roll, or reset — network-event-bus.ts:295 subscribes at `afterSeq: H`), a paired remote client has no way to learn that a host run is live: all three liveness reads are unregistered (`get_agent_run_status_unified` — capability_ledger.rs:3413; `get_agent_conversation_runtime_statuses` — :1897; `is_agent_running` — :1888), and the registered read carrying the same truth (`get_agent_conversation_runtime_index`, registry.rs:1791) is wired only to AgentsComposerWorkspaceChangesCard.tsx:826, never to chat status. `agentStatus` therefore stays `idle` (chatStore.ts:748 default) until the run's terminal lifecycle event, since useAgentEvents.ts:430-436 deliberately ignores `agent:chunk` for UI state. Consequences: no typing indicator or activity label (ChatMessageList.tsx:1143-1150 via IntegratedChatPanel.tsx:624), the composer picks the idle-continuation send path, and — because `shouldShowStop` requires `generating` (AgentComposerSurface.tsx:470) — the Stop button never renders, defeating the deliberate `ui:operate` registration of `request_remote_agent_stop` that agent-gate.ts:110-116 says exists so "brakes must not need ui:agent". A warm cursor-validated resume is NOT affected (it replays durable `agent:run_started` at network-event-bus.ts:273). Secondary: the three refused reads sit on 1.5s/5s/5s repeating polls — the runtime-status one explicitly keeps polling on error (useAgentConversationRuntimeStatus.ts:143) — so a paired client also runs a permanent REMOTE_COMMAND_UNAVAILABLE poll storm. The fix seam already exists in-repo: pending-gate-reconcile.ts solves this identical "backend-memory state the event log cannot replay" problem for permission/question gates by re-asking the host on every connect.

#### [MAJOR] Queued-message delete and edit report success locally while the host's queue keeps the message — edit delivers the turn twice

***CONFIRMED** (high confidence)* · `frontend/src/hooks/useChatActions.ts:492`

**Claim.** `handleDeleteQueuedMessage` and `handleEditQueuedMessage` remove the message from the local store first and then swallow the backend failure; `delete_queued_agent_message` is absent from `facade_ops`, so on a paired client the host-side queue entry is never removed.

**User-visible failure.** On a remote client the user sends a message into a live codex run, sees the queued chip, decides against it and taps Delete. The chip vanishes; the host still holds the queue entry and delivers it on the next drain. Worse, tapping Edit deletes it locally, silently fails on the host, and sends the edited text — so the agent receives both the original and the edited turn.

**Evidence.** frontend/src/hooks/useChatActions.ts:485-496 — `deleteQueuedMessage(storeContextKey, messageId)` runs first, then `await chatApi.deleteQueuedAgentMessage(...)` inside `try { } catch { // Silently ignore — local state already updated }`; the same delete-before-send pattern at :566-570 precedes an unconditional `sendAgentMessage`. api/chat.ts:5543 invokes `delete_queued_agent_message`, which is not in `facade_ops`. The queue chip is reachable remotely because `sendRemoteChatMessage` returns `wasQueued: true` + `queuedMessageId` (api/chat.ts:5410) and useChatActions.ts:305/369 writes it straight into the store via `queueAcceptedMessage`; chips are only suppressed for `interactive` (claude) harnesses while a run id is known (IntegratedChatPanel.tsx:976-989), so codex conversations — and any claude conversation after the run id clears — show them.

**Verifier adjustment.** On a paired remote client with `ui:agent`, `handleDeleteQueuedMessage` (useChatActions.ts:485-496) and `handleEditQueuedMessage` (:557-596) swallow the host's `REMOTE_COMMAND_UNAVAILABLE` for `delete_queued_agent_message` — a command the ledger marks `registered: false, class: denied, "deletes a durable entity"` — while mutating local state regardless. Delete removes the chip but leaves the host queue row, which is still drained by `process_queued_messages` inside the live run. Edit additionally resends unconditionally via `sendAgentMessage` → `sendRemoteChatMessage`, creating a second host row, so the agent receives both the original and the edited turn. `get_queued_agent_messages` is likewise unregistered, so `useQueuedMessagesHydration` fails silently and the divergence is never reconciled or surfaced. Unlike `handleSendQueuedMessageNow`, which re-queues and calls `reportSendFailure`, these two paths have bare `catch {}`. Note: in the edit handler the backend delete precedes the local delete (the original claim had the order reversed); the defect is unaffected.

#### [MAJOR] Attachment upload is enabled on a remote client but no attachment command is exposed, and the remote send drops attachmentIds anyway

*plausible — not adversarially verified (below the verification severity bar)* · `frontend/src/components/Chat/IntegratedChatPanel.tsx:1920`

**Claim.** `enableAttachments` is computed purely from `effectiveConversationId && !isHistoryMode` with no remote condition, so the paperclip and drag-drop stay live while `upload_chat_attachment`/`delete_chat_attachment` are absent from `facade_ops` and the remote send path never forwards attachment ids.

**User-visible failure.** A remote user drags a screenshot into the composer. ## GitHub

The GitHub domain is the least-covered surface of the remote feature: the entire `github_commands` module is ledgered Elevated/`spawnsProcess`, `git_commands` is denied, `publish_agent_conversation_workspace`/`close_agent_workspace_pr` are denied, `get_agent_conversation_workspace` is host-denied-spawns-process, and the Review PR context route is an explicit `REMOUNT_DENIED_SINKS` entry. Instead the failures degrade three ways, all bad: (a) surfaces that vanish silently because they key off a workspace object the client can never load (Review PR card, Publish/Commit & PR tab, PR detail panel) while the sidebar keeps painting `PR #N` badges from the registered `list_remote_agent_sidebar_conversations` twin that *already carries* the full workspace projection; (b) surfaces that invert an unavailable read into a false claim about host state (GitHub reads as "Not authenticated"/"gh missing" with "Install the GitHub CLI" guidance, GitAuthRepairPanel raises a permanent "Git & GitHub Access" alarm, the GitHub PR Mode toggle paints OFF while `github_pr_enabled: true` is on the wire); and (c) live-looking buttons that optimistically move a Kanban task before an invoke that can never succeed (`retry_merge`). Events themselves are fine — `pr_review_artifact:*`, `agent:workspace_changed`, `notification:*` and `task:merge_*` are all Durable, and publication polling rides a registered read — so this is a client-presentation and gating gap, not a fan-out gap.

- **Mid-session authority changes and environment switching** — Scope *narrowing* is safe (`set_agent_control_with_context` tears down sessions, `remote_device_commands.rs:347-357`), but *widening* does not, so a freshly-granted device stays visibly gated until it reconnects. Untested: a query created under env A whose refetch fires after the user switches to env B — `invoke` resolves `getTransportEnvironmentId()` at call time (`lib/remote/invoke.ts:54`), so routing is global while caches are keyed.
- **Event-log retention vs cursor resume, epoch roll, rate limiting** — `retention.rs`, `sequencer.rs` (`cursor_pruned`/`epoch_changed` resets) and `rate_limit.rs`/`request-pacing.ts` are the substrate every domain's freshness claim rests on, and no sweep exercised them. The automations and GitHub sweeps both concluded 'reconnect closes the gap' without testing what a client does when its lease expired and its cursor was pruned.
- **Attachment endpoint and host-path leakage beyond conversations/ticketing** — `/remote/v1/attachments/:id` exists on the host and has no client consumer (documented census B-row). Host-path containment was only audited for the sidebar twin and ticketing DTOs; nothing checked task/merge/artifact/automation/workflow DTOs for `worktree_path`, `working_directory`, or absolute log paths.

## Method

Produced by a 23-agent adversarial workflow on branch `feat/remote-multi-env` (2026-08-01): four parallel domain reviewers traced every user-visible capability through `remote_server/registry.rs`, `capability_ledger.rs`, `fetch_remount.rs`, the `ralphx-remote-protocol` event classification, and the frontend gates/transport; every critical/major finding was then handed to an independent skeptic instructed to refute it from the code (defaulting to refuted when ambiguous); a completeness critic reviewed the merged result. Findings marked CONFIRMED survived refutation; refuted claims are listed per domain for transparency; minor/info findings were not individually re-verified.
